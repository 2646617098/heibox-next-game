# heibox-next-game

「下一个玩什么」：读取用户自己的 Steam 游戏库，按游玩风格从库里挑一款推荐并说明理由。
也可以「纯随机」抽一款 —— 那条路径完全不看口味。

## 命令

```bash
npm install
npm run hb-sdk -- login          # 需要浏览器授权
npm run hb-sdk -- remote bind <mini-program-id>
npm run dev                      # 调试台 http://127.0.0.1:5174
npm run build
npm run check                    # 推荐算法自检（32 条断言），不依赖 SDK
npm run build:metadata           # 重新生成游戏标签数据集（见下）
npm run probe                    # 直接问 Host：游戏库到底返回哪些字段
npm run verify                   # 无头 Chrome 进调试台读真实渲染结果
npm run deploy -- --release-note "更新说明"
```

`npm run verify` 与 `npm run probe` 需要 `npm run dev` 正在运行，并且有一个带
`--remote-debugging-port=9222` 的 Chrome 打开了调试台地址。两个脚本的文件头都写了做法。

## 结构与分工

| 文件 | 职责 |
| --- | --- |
| `src/library.js` | 数据层：分页拉库、合并标签数据集、字段探针与字段普查、失败回退演示数据 |
| `src/game-metadata.js` | 打包标签数据集的查询与合并层 |
| `src/recommend.js` | 算法层：纯函数。风格画像 + 候选打分 + 模式判定 |
| `src/demo-library.js` | 内置演示库（30 款），仅在读不到真实库时使用 |
| `src/main.js` | 界面层：状态、渲染、深链、握手与生命周期订阅 |
| `src/data/game-metadata.json` | 打包的游戏标签数据集（构建产物，应随仓库提交） |
| `scripts/build-appid-seed.mjs` | 种子生成器：从 Steam 热度榜 + 热销榜取 appid，与个人库种子合并 |
| `scripts/build-game-metadata.mjs` | 数据集生成器（开发期跑，抓 Steam 商店页热门标签） |
| `scripts/check-recommend.mjs` | 算法自检：断言 + 排名对照 + 文案抽样 |
| `scripts/verify-browser-mock.mjs` | 用无头 Chrome 进调试台读真实渲染结果 |
| `scripts/probe-host-payload.mjs` | 绕开业务代码直接问 Host 返回哪些字段；可导出 appid 清单 |

## 平台能力边界（实测结论）

只依赖 **`steamLibrary`** 权限，它**声明即可用、不需要平台批准**（`hb-sdk remote info` 会
显示 `steamLibrary: 需申请=否 最终=可用`）。`network` / `companion` 是 `需申请=是 批准=否
最终=不可用` —— 项目**一个都没用**，所以不会被未开放权限卡住。

**游戏库里到底有什么**（876 款实测，`npm run probe` 可复现）：

```
appid / steamAppid / name / image / icon / playtime2Weeks / playtimeForever
```

七個字段，全部 100% 覆盖（`icon` 875/876）。**`tags` 与 `price` 从未出现** —— 三种排序、
关键字搜索、`includeHidden` 共 6 组参数全试过，键名恒定。

所以「按游玩风格推荐」所需的游戏元数据，平台**不提供**。可用的替代路径只有：
`navigation.openAppPage({ target: 'game_detail', appId })` 能把用户**带到**官方游戏详情页
（那里有标签和平均游玩时间），但它返回 `void`，**读不到值**，只能用于让用户核对。

### 已知限制：扫码真机调试读不到游戏库

**现象**（2026-10，小黑盒 Android `1.3.396` + SDK `0.9.1`）：从调试台扫码进入真机后，
`user.getSteamGameList()` 每次都在 **10001 ms** 后以 `REQUEST_TIMEOUT` 失败，连续 6 次
一次都没回来；同一时刻 `user.getInfo()` **成功**返回（`logged-in`），浏览器 Mock 用同一份
构建、同一个账号读到 **876 款**。

已排除的因素（都有日志）：`steamLibrary` 在 runtime 快照里 `enabled`；客户端版本高于
基线 `1.3.390`；账号已登录且 `steam_account=granted`；查询参数四种组合（默认 / `weeks`100 /
`all`20 / `all`100）全部同样超时；冷启动的账号上下文轮换已经修掉（`reason=quiet`）。

**结论**：请求已经送到客户端，但**调试容器那一层没有应答**；把同一版本 `remote deploy`
并发布后，**线上运行时能正常读取游戏库**。所以这是「扫码真机调试容器」的限制，不是账号、
网络、权限或查询参数的问题，应用代码也无法绕过（SDK 单次调用上限固定 10 秒，公开 API
里没有替代通道）。

**对开发的约束**：

- 扫码调试只用来验收 UI、导航栏、深链、生命周期这些**不依赖游戏库**的部分；
- 涉及游戏库的逻辑，用**浏览器 Mock**（数据来自 CLI 登录态）或**线上/预览版本**验收；
- 页面底部「诊断信息」默认收起，真机出问题时先看它的「账号上下文」和「请求 N」两行。

## 游戏标签数据集

因为平台不给标签，项目自带一份打包数据集，由 `scripts/build-game-metadata.mjs` 在开发期
生成，随包发布，**运行时不联网**。

- **来源**：Steam 商店页（`store.steampowered.com/app/<appid>/`）的「热门用户标签」区块，
  用 `?l=schinese` + `Accept-Language: zh-CN` 固定取简体中文，每款取前 20 个标签。
- **规模**：当前收录 **11,171 款**游戏（有标签 11,169 款，平均 18.5 个标签，
  去重后 427 个标签），数据集 868.8 KiB。
- **合规**：这是抓取第三方页面，**数据来源的合规责任在开发者**，上架前需要自行确认。
- **生成**：`npm run build:metadata`。增量续跑（已抓过的跳过，每 25 款落盘），
  6,700 款约 3.5 小时。
- **必须加 `--use-system-ca`**：Node 自带 CA 列表不含该站点的中间证书，否则 fetch 会以
  `UNABLE_TO_VERIFY_LEAF_SIGNATURE` 失败（npm 脚本里已经带上）。
- **覆盖策略**：接口给标签就用接口的，接口没给就用数据集，两者都没有则标记为无标签并
  **退回行为策略**，同时界面上明确说明当前是降级状态。

### 存储格式：字典 + 索引

数据集用 `encoding: "dict+index"` 存储 —— 一张去重后的标签字典 + 每款游戏一组整数索引：

```json
{
  "encoding": "dict+index",
  "dict": ["2D", "动作", "第一人称射击"],
  "games": { "10": [1, 2, 0], "730": [1, 2] }
}
```

（`games` 里的数字是 `dict` 的下标；空数组表示该游戏抓到了但没有标签。）

这不是省字节的洁癖，而是**启动开销**。当前数据集 11,171 款、标签出现 20.6 万次，
如果直接存字符串，小程序启动时要创建 20 万个字符串对象；字典化后只需创建字典里的 427 个，
标签在查询时按需还原并缓存。

| | 直接存标签 | 字典 + 索引 |
| --- | --- | --- |
| 数据集 | 2570.5 KiB | **868.8 KiB**（−66%） |
| 启动创建的标签字符串 | 206,721 | **427**，其余按需 |
| 产物合计 | 约 2.7 MiB | **990.1 KiB**（占上限 0.97%） |

查不到的标签一律返回 `null`（区别于"查到但没有标签"），上层据此决定是否降级。

### 收录哪些游戏：种子决定覆盖率

数据集是按 appid 白名单抓的，所以"种子包含哪些游戏"直接决定推荐质量。只拿某个人的库当
种子，别人用就会大面积空标签。种子由 `scripts/build-appid-seed.mjs` 生成，合并两个来源：

| 来源 | 参数 | 作用 |
| --- | --- | --- |
| 最受推荐（≈拥有量） | `sort_by=Recommendations_DESC&category1=998` | 覆盖大众与长尾，主力来源 |
| 当前热销 | `filter=topsellers&category1=998` | 保证新出的热门游戏也在里面 |

再与已有种子**合并**，所以个人库里的游戏不会因为重新生成种子而丢失。

```bash
npm run build:seed -- --popular 3000 --topsellers 500   # 默认规模
npm run build:metadata                                  # 然后抓标签（增量续跑）
```

两个实测坑，都已在脚本里处理：

- **`sort_by=Reviews_DESC` 排序不生效**（返回冷门独立游戏），要用 `Recommendations_DESC`。
- **Steam 会限流**：连续请求约 36 次后开始返回 429。种子生成器和数据集生成器都带指数退避；
  数据集生成器把限流记为 `retryable` 而**不是**"这个游戏没有标签" —— 否则下次运行会直接
  跳过，那批游戏就被永久丢掉了。带 `retryable` 的条目会在下次运行时自动重抓。

数据集是**静态**的：Steam 新上架的游戏、以及已有游戏标签的变化都不会自动进来，需要重新
跑一次生成器（增量，只补新游戏）并重新提审。想要"任意游戏都能实时查"需要 `network` 权限 +
自建后端，而 `network` 目前平台未开放批准。

## 推荐怎么算的

**1. 风格画像**：取「最近两周有游玩」的游戏，把每款游戏的时长按标签的 **IDF 比例**分配
（特色标签拿大头、通用标签拿小头），累加并归一化成一张口味分布。近两周全为 0 时回退到
累计时长。

IDF 这一步不能省。均摊权重下，实测真实库 874 款里「单人」出现在 712 款、「独立」400 款，
画像头号标签会是「单人」，推荐理由变成「按你最近的『单人』口味挑的」—— 等于没说。
加上 IDF 后头号标签变成「卡牌战斗」，备选全部收敛到卡组构建类，与最近的游玩记录一致。
`npm run check` 里有对应断言（通用标签权重必须低于特色标签）。

**2. 候选池**：排除最近两周正在玩的游戏（它们不需要被推荐）。

**3. 打分**：

```
最终得分 = 口味契合度 × 0.7 + 候选池加成 × 0.3
```

契合度用 cosine 相似度，天然惩罚「标签堆砌」的游戏。候选池加成：买了没玩 `1.0`，
久未启动 `0.75`。两个权重都透出到界面的「打分构成」里，改完跑 `npm run check` 看排序变化。

**4. 并列排序**：依次按「匹配到的标签数」→「行为信号（累计时长）」→「名称」。
最后用名称只为顺序确定，**不代表优劣**。

**5. 模式**：一款候选都没对上标签时，模型进入 `behavioral` 模式 —— 排序实际由候选池与
行为信号决定，界面会换成「从吃灰的库里挑的」并明确说明没有风格依据，
**不会把一个无依据的顺序伪装成推荐**。

## 为什么没有「预计投入多少小时」

曾经做过，后来**整条链路删掉了**。原因是拿不到可信的数据源：

| 候选源 | 结果 |
| --- | --- |
| 平台接口 | `getSteamGameList` 只给 7 个字段，没有游戏长度 |
| SteamSpy（`average_forever`） | Cloudflare 挡住 |
| HowLongToBeat（真实通关时间） | Ziff Davis 防护，接口返回 `403 Unavailable (IFW-E01)` |

两边都是刻意设置的反爬，**不绕**。于是只剩「手写标签先验 + 个人投入校准」这一条路，而它的
输出只有四个值：`{ short: 6, medium: 18, long: 45, endless: 80 }` 小时。实测在 11,171 款
数据集上 **77% 的游戏都算成 45 小时**，在你自己的 871 款候选里 45h 与 80h 合计占 78% ——
这不是估算，是分档，而且四个数字是手写的。

试过改用「标签最像的已玩游戏的实际投入时长」直接当估算，结果更糟：只可能取 5 个值，且有
168 款游戏都被算成 348 小时（因为《怪物猎人：世界》玩了 348 小时）。`playtimeForever` 是
「你玩了多久」，不是「这游戏多长」—— 这个坑踩过两次。

结论：**给不出准确小时数，就不假装精确。** 时长偏好筛选、档位估算、校准、界面文案全部移除
（`src/duration.js` 已删除）。

## 界面结构

页面从上到下：数据来源标识 → 可能出现的提示条 → **三选一的状态区**（加载中 / 失败 / 结果）
→ 结果区内部为「推荐卡 → 打分构成 → 口味画像 → 换一个 / 纯随机」。

**打分构成与口味画像都默认展开**，点标题可收起。两者都用原生 `<details>`，折叠状态由浏览器
维护，不需要 JS，也不会有"属性说隐藏、画面还在"的问题。收起一个不影响另一个。
全部展开就是"内容最长"的状态，正好被用来自检滚动条是否挤压视口。

**两种取推荐的方式，并列在底部：**

| 按钮 | 作用 | 卡片口径 |
| --- | --- | --- |
| 换一个 | 按评分从高到低循环前进 | 「按你最近的『X』口味挑的」+ 打分构成可见 |
| 纯随机 | 在候选池里**均匀随机**抽一款，不参考口味、标签或评分 | 「随机」+ **隐藏打分构成** |

随机模式必须换一套说法：它是"没看任何依据"的结果，沿用"按你的口味挑的"就是骗人；
「打分构成」也要隐藏，否则会暗示分数决定了选择。随机抽取会避开当前展示的那款，
所以每次点击都一定换到别的游戏。

**没有备选列表。** 翻推荐只有这两个入口 —— 代价是**没有「回到首选」按钮**，
换过之后要回到第 1 名只能重新加载页面。

## 界面状态机的四个坑

**① `hidden` 属性必须真的隐藏。** `styles.css` 里有一条兜底规则：

```css
[hidden] { display: none !important; }
```

看起来很冗余，但它是必需的：HTML 的 `hidden` 靠**浏览器默认样式表**里的 `display:none`
生效，而作者样式表里的 `.state { display: flex }` / `.result { display: flex }` 优先级更高，
会把它盖掉。结果是 `el.hidden = true` 设置成功、属性读出来也是 `true`，**元素却照样显示** ——
加载中、错误、结果三个区块会同时堆在页面上。

**② 验证必须看"实际是否渲染"，不能看属性。** `scripts/verify-browser-mock.mjs` 用
`checkVisibility()` / `getClientRects()` 判断，因为 `getComputedStyle(子元素).display`
**不反映祖先被隐藏**（会把隐藏区块里的按钮误报成可见）。同时断言三个区块里**有且仅有一个**
可见，并支持 `SCREENSHOT=<path>` 截图做视觉确认。

**③ 滚动条不能挤压视口。** `html` 上固定保留滚动条槽位：

```css
html {
  overflow-y: scroll;          /* 所有引擎都生效 */
  scrollbar-gutter: stable;    /* 支持的引擎上语义更准确 */
}
```

不预留时，展开折叠面板让页面变高，竖向滚动条突然出现会占掉约 10px 视口宽度，
而 `.app` 是 `width: min(100%, 560px)` + `margin: 0 auto`，于是整页变窄并左移 ——
用户看到的就是「点展开后往左缩一下」。

**验证这类问题必须用真实滚动条**：给无头 Chrome 加 `--hide-scrollbars` 会让滚动条宽度变 0，
从而把这个 bug 完全掩盖掉（我第一版验证就踩了这个坑，测出来"通过"但实际没测到）。
`scripts/verify-browser-mock.mjs` 现在会测量展开前后 `documentElement.clientWidth` 与
`.app` 的位置/宽度，要求**完全不变**，并额外断言"展开后确实发生了滚动"（否则等于没测到场景）。

**④ 任何退出加载态的分支都必须渲染终态。** 曾经的写法是读完数据后
`if (destroyed) return;` —— Runtime 被终止（CLI 离线、会话过期、开发服务重启）时会**静默退出**，
界面永远停在「正在分析你的游戏库」，连重试按钮都渲染不出来。现在：

- `unload`（Runtime 终止）→ 渲染终点状态，只给「重新加载页面」（SDK 上下文不可恢复，重试无意义）；
- 读取走**空闲看门狗**（20 秒没有新数据才超时，不是整轮总超时，所以大库分页慢不会误杀）；
- 读取与渲染都包在 try/catch 里，失败一律落到 `showFailure`。

底部「已读取 N 款 / 共 M 款」的进度提示也是为此加的：876 款要发 10 次分页请求，
界面必须让人看出在推进，而不是像卡住了。

## 算法调参口

`src/recommend.js`：

```js
AFFINITY_WEIGHT = 0.7   // 口味契合度权重
POOL_WEIGHT     = 0.3   // 候选池加成权重
POOL_BONUS = { unplayed: 1, backlog: 0.75 }  // 买了没玩 / 久未启动
```

`src/game-metadata.js` 只看数据集，没有可调项；要扩充覆盖改种子规模后重跑生成器。

改完跑 `npm run check` 看排名与文案变化。

## 上线流程

### 1. 本机测试

调试服务已在运行时，**http://127.0.0.1:5174/** 是调试台。真实客户端验收有两个入口：

| 入口 | 操作 | 覆盖 |
| --- | --- | --- |
| PC 客户端 | 点调试台右上角**桌面图标** → 选正式版 / Debug 版 | `windows` |
| 手机真机 | 点**二维码** → **选对局域网网卡** → 小黑盒 APP 扫码 | `android` / `ios` / `ohos` |

手机扫码失败的**头号原因**是网卡选错：机器上有 WSL、VMware 等虚拟网卡时，必须选手机能连到的
那块（通常是 `WLAN` 那张）。

真实客户端能验证浏览器 Mock 测不到的东西：Host 的 Runtime Gate、真实分页、真机字体与安全区。
调试期间 **CLI 必须保持在线**，连续失联约 30 秒会销毁 Runtime。

### 2. 提交审核

```bash
npm run hb-sdk -- remote deploy --release-note "首个版本：按口味从 Steam 库推荐下一个游戏"
```

它会重新构建 → 上传缺失文件 → 提交审核。部署期间不要有其他进程改 `dist/`；中断后重跑同一条
命令即可续接。

### 3. 发布

审核通过**不会自动上线**，需要手动发布：

```bash
npm run hb-sdk -- remote versions              # 查版本与状态
npm run hb-sdk -- remote preview <version>     # 预览线上展示
npm run hb-sdk -- remote release <version>     # 正式发布
```

首次上线不建议用 `--auto-publish`：手动发布前可以用 `remote preview` 确认名称和封面。

远端名称现在显示「我的小程序」，**发布后才会更新**为 `package.json#heybox.name` 的值。

## 发布前检查

`package.json#heybox.platforms` 目前声明全平台，请按**实际完成真机验收**的平台保留，
未适配的平台务必删除（但不可清空，空数组会直接抛错）。`linux` 没有客户端基线，不建议声明。

图标与封面由 `scripts/build-brand-assets.py` 生成：

```bash
python scripts/build-brand-assets.py   # 需要 Pillow；换图标/改封面文案后重新生成
```

| 文件 | 来源 | 尺寸 | 大小 |
| --- | --- | --- | --- |
| `assets/icon.png` | `assets/icon-source.png`（彩色转盘设计稿）缩小 + 轻度锐化 | 200×200 | 38.6 KiB |
| `assets/cover.png` | 代码绘制（配色取自 `styles.css`） | 510×272 | 42.5 KiB |

图标改成"位图设计稿 → 规范尺寸"的流程：设计稿 1254×1254 无法用绘图代码忠实复现，
脚本只做居中裁方 + LANCZOS 缩小 + `UnsharpMask`，保证重新生成的结果和仓库里的
`icon.png` 一致。换图时替换 `assets/icon-source.png` 再跑一次脚本即可。

两者会被复制到 `dist/_hb/basic-info/` 并计入整包签名与 100 MiB 预算；构建时会用 sharp 校验
真实格式与尺寸。**不要**用 `heybox-placeholder.png`（已删除）。

尺寸按《小程序工坊上架规则》第十二条设计规范：图标 200×200、封面 510×272。
`heybox.category` 已设为 `tool`；`heybox.desc` 自 SDK **0.9.1** 起支持，本项目已升级到 0.9.1，可以在
`package.json` 里声明。
